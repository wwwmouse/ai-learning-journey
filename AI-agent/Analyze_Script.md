# Agent 脚本学习 SOP

> **定位：** 一套轻量的脚本分析与学习流程，不是考核清单，也不是代码审计规范。
>
> **目标：** 用有限的时间理解一个脚本真正值得学习的工程机制，并将有价值的理解沉淀回源代码。
>
> **适用范围：** Python 等可执行脚本，包括产品代码、测试代码和实验代码。不负责配置文件、文档的系统性分析。
>
> **协作方式：** 学习者先思考，AI 导师负责引导、提示、纠错和审查，不直接替学习者完成全部分析。

---

## 0. 学习原则与整体流程

### 0.1 核心原则

1. **机制优先于语法：** 重点理解代码为什么这样设计，而不是逐行翻译。
2. **重要度决定阅读深度：** 不要求理解每一行代码。
3. **先思考，再验证：** 对核心机制先形成自己的判断，再通过代码和实验验证。
4. **关注职责边界：** 区分程序、模型、框架和外部服务各自承担的责任。
5. **关注前后联系：** 新练习不是孤立的，要明确它相对于之前练习新增、替换或改进了什么。
6. **理解优先于覆盖率：** 没必要为了完成清单而强行理解所有辅助代码。

### 0.2 分析流程

定位脚本 → 按重要度分层 → 追踪核心机制 → 理解与验证 → 对照前序练习 → 沉淀注释。

默认采用快速分析。只有遇到新的核心机制、难以理解的控制流或重要设计决策时，才深入研究。

### 0.3 与课程学习循环的关系

课程的六步学习循环：

看成果 → 直接执行 → 选小改动 → 先猜 → 再跑 → 说出原因。

本 SOP 重点负责前两步的理解准备，以及后续核心机制的分析。

真正的代码修改、实验和验证应结合当前练习目标进行，不要求每个脚本都完成一次额外改造。

## 1. 定位脚本（约 5 分钟）

### 1.1 区分脚本类型

| 类型 | 主要关注点 |
|---|---|
| `starter*.py` / 产品代码 | 数据流、控制流、核心机制、边界 |
| `test*.py` / 测试代码 | 验证了哪些契约、覆盖了哪些情况、遗漏了什么 |
| 实验脚本 | 实验变量、预期结果、实际结果、结论边界 |

### 1.2 快速确定三个位置

- **入口：** 从哪里开始执行？例如 `main()`、`run()` 或测试函数。
- **出口：** 最终返回什么？有哪些可能的结束状态？
- **外部依赖：** 是否调用模型、网络、文件、数据库或其他服务？调用集中在哪里？

不要求完整阅读文件，只需要先建立整体轮廓。

### 1.3 先运行，再阅读（条件允许时）

如果脚本提供了明确的运行方式：

1. 先看预期成果和成功条件。
2. 尝试直接运行。
3. 观察输出、异常和执行路径。
4. 如果依赖尚未配置，不要在环境问题上消耗过多时间，先转向可离线验证的部分。

注意：运行成功只说明当前路径能够执行，不代表所有行为都正确。

## 2. 按重要度分层（约 5–10 分钟）

本 SOP 的主要工具。

| 档位 | 分类依据 | 阅读方式 |
|---|---|---|
| ⭐ 核心 | 承载本练习最重要的设计思想；换框架或语言仍有学习价值 | 深入理解执行过程和设计原因 |
| 🟢 必读 | 核心机制的实现边界，例如 Schema、验证、路由、状态更新 | 理解输入、输出、约束和失败形式 |
| 🟡 看关键 | 辅助核心流程的外层逻辑，例如异常处理、初始化、清理 | 只看关键分支和职责 |
| ⚪ 可跳过 | 业务细节、环境胶水、重复性封装 | 作为黑盒，知道作用和调用方式即可 |

### 两个辅助判断问题

1. **拿掉这段代码，核心机制还成立吗？**
2. **换一个业务场景或技术框架，这段代码体现的思想还成立吗？**

注意：不能单纯以「删掉后脚本还能不能运行」判断重要性。

有些代码虽然不直接决定脚本能否运行，却决定了安全性、正确性或可测试性，仍然可能属于核心机制。

经验上，学习脚本中通常有相当一部分代码可以作为黑盒。若感觉每行都重要，可以先往下读，再回头调整分层。

---

## 3. 核心机制分析（约 15–25 分钟）

只对 ⭐ 和 🟢 进行重点分析。

### 3.1 ⭐ 核心代码：理解机制

对于每个核心函数、类或关键代码块，重点回答：

- 它解决什么问题？
- 输入是什么，输出是什么？
- 它依赖哪些状态或外部对象？
- 它修改了什么数据？
- 它如何决定下一步？
- 正常情况如何结束？
- 失败时会发生什么？

优先追踪一条完整执行链路：

入口 → 核心函数 → 关键分支 → 外部调用 → 返回或结束。

不要求把所有函数都展开，只追踪理解机制必需的部分。

### 3.2 🟢 必读代码：理解约束

重点记录：

- 输入约束：类型、必填字段、允许值。
- 输出契约：返回值、数据结构、状态。
- 失败形式：异常、错误对象、拒绝执行或重试。
- 边界保护：白名单、Schema、验证器、权限限制等。

### 3.3 控制流与状态

遇到 Agent、Workflow 或多步骤程序时，额外关注：

**控制流：**
- 谁决定下一步？
- 是程序硬编码决定，还是模型动态决定？
- 是否存在循环、分支、暂停、恢复或终止条件？
- 是否有最大步数或调用次数限制？

**状态：**
- 跨步骤共享的数据是什么？
- 状态由谁创建、读取和修改？
- 数据通过参数、消息历史、State、Context 还是其他机制传递？
- 状态什么时候清理或持久化？

### 3.4 职责边界

重点区分：

| 参与者 | 重点分析 |
|---|---|
| 程序 | 硬约束、流程控制、验证、异常处理 |
| 模型 | 理解、生成、选择工具、动态决策 |
| 框架 | 封装了哪些流程、状态和调用机制 |
| 外部服务 | 提供什么能力，带来什么依赖和失败风险 |

不要求每个脚本都涉及全部参与者。

### 3.5 核心机制的三问

1. **为什么这样设计？**
2. **拿掉或替换它会怎样？**
3. **真实环境还缺什么？**

第三问尤其关注教学实现与实际工程之间的差距，例如超时、重试、鉴权、持久化、观测、费用限制和人工审批。

## 4. 与前序练习对照（约 5–10 分钟）

这是理解新机制的重要步骤，但不要求每个脚本都做完整横向比较。

优先回答三个问题：

1. **新增了什么？** 本练习引入了之前没有的机制吗？
2. **替换了什么？** 是否使用另一种方案解决之前已经出现的问题？
3. **改变了什么？** 控制权、状态管理、职责边界或验证方式发生了什么变化？

例如：

- 手写 Agent Loop → 框架封装的 Agent Loop。
- JSON Tool Calling → CodeAct。
- 自由文本输出 → Schema 约束输出。
- 顺序执行 → 图式分支与恢复。
- 程序管理状态 → 框架 Checkpoint。

对照的目的不是判断哪个框架更好，而是理解不同方案的设计取舍。

如果当前练习没有明显的前序对照，简要说明即可，不要强行制造联系。

---

## 5. 分析收尾与自查

分析结束时，尝试用自己的话说明：

- **它做什么：** 输入、输出和主要用途。
- **它怎么做：** 核心执行链路与关键机制。
- **状态在哪里：** 哪些数据跨步骤存活，由谁管理。
- **谁做决定：** 程序、模型和框架各自拥有什么控制权。
- **它的边界：** 失败时如何处理，哪些能力没有实现。
- **它的新价值：** 相比之前的练习增加了什么理解。

最后保留课程要求的三句话：

1. 为什么这样写？
2. 拿掉它会怎样？
3. 真实环境还缺什么？

这不是打分环节。说不清的地方只补对应的代码，不需要重读整份脚本。

## 附 A：遇到问题怎么办

1. 先看终端中最早出现的真正错误，不要只看最后一行。
2. 找到当前练习的成功条件和对应测试。
3. 检查失败发生在程序自身、模型调用还是外部环境。
4. 尝试缩小问题范围，优先验证核心机制。
5. 仍然无法理解时，记录一个具体问题，暂时继续后续内容。

不要为了弄懂一个辅助函数而中断整个学习流程。

---

## 附 B：常见分析误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 逐行翻译 | 知道语法，却不理解机制 | 先找链路和核心设计 |
| 把框架当黑盒 | 不知道框架接管了什么 | 追踪框架调用前后自己的职责 |
| 把模型和程序混为一谈 | 不清楚是谁做出的决策 | 区分模型决策与程序硬约束 |
| 只看成功路径 | 忽略异常和边界 | 至少分析一种重要失败路径 |
| 测试全绿就认为没问题 | Mock 可能绕过真实依赖 | 明确测试覆盖范围 |
| 过度分析辅助代码 | 时间花在低价值细节上 | 按重要度分层 |
| 只看当前脚本 | 学习变成孤立知识点 | 对照前序练习 |
| 把 API 用法当成设计思想 | 换框架后知识无法迁移 | 提炼 API 背后的机制 |

## 附 C：把理解写进脚本（必须遵守）

分析的最终产出是**源代码中的高价值注释**，不额外生成单脚本分析报告。

只写日后回看有价值、又不容易重新推导的内容。

### C.1 文件开头导语

对于有一定复杂度的脚本，建议在开头添加 3–6 行说明：

- **链路：** 谁调用谁，主要执行几步。
- **状态：** 哪些数据跨调用存活，由谁持有。
- **出口：** 有哪些结束方式或返回结果。
- **核心机制：** 本脚本最值得学习的设计是什么。

简单脚本不强制添加完整导语。

### C.2 关键函数标记

使用重要度标记：

- ⭐ 核心
- 🟢 必读
- 🟡 看关键
- ⚪ 可跳过

只标记真正有价值的函数或代码块，不需要给每个函数贴标签。

### C.3 注释写作规范

- 解释为什么这样设计，不复述代码已经表达的内容。
- 优先说明职责边界、关键约束、容易忽略的行为和失败条件。
- 用函数名、类名和 API 定位，不写容易失效的行号。
- 不要把尚未验证的推测写成确定事实。
- 如果某项行为尚未运行验证，明确标注「待确认」。
- 保留已有的有效注释，不为统一格式而大规模改写。

## 附 D：AI 导师协作规范

AI 导师应遵守以下方式：

### D.1 一次聚焦一个问题

不要一次抛出大量问题，也不要在用户尚未思考时直接给出完整分析。

每次优先围绕一个关键机制展开。

### D.2 先让学习者判断

优先使用以下方式引导：

- 你认为这段代码解决什么问题？
- 如果拿掉这部分，会发生什么？
- 这里是谁决定下一步？
- 这份数据是从哪里来的，又由谁修改？
- 你觉得框架接管了哪部分工作？

根据回答决定下一步提示，而不是机械执行全部问题。

### D.3 提示与纠错

- 判断正确：解释为什么成立，并指出适用边界。
- 部分正确：指出缺失的关键环节，给出适量提示。
- 判断错误：先指出具体错误，再引导重新推导。
- 完全没有思路：从执行链路、输入输出或简单示例开始拆解。

除非用户明确要求，否则不直接给出完整答案或整段实现。

### D.4 代码审查

用户完成分析或实验后：

1. 检查理解是否符合实际代码。
2. 区分概念错误、逻辑错误和表述不准确。
3. 指出遗漏的重要边界。
4. 建议哪些内容值得写进代码注释。
5. 不要求为了形式完整而添加无价值注释。

### D.5 维持学习连续性

分析新脚本时，应尽可能联系当前 Stage 的学习目标和之前已经掌握的机制。

不要把已经理解的概念每次重新讲一遍；只有出现新的差异或更深层的应用时，才展开说明。

---

## 时间盒

- 普通脚本：约 45 分钟。
- 核心机制较多或控制流复杂的脚本：允许适当延长。
- 超时仍未理解的非核心问题：记录疑问，继续学习。

**最终原则：用最少的阅读时间，抓住最值得迁移的工程机制。**
