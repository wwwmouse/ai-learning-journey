# Stage Learning Notes — 通用阶段总结 Prompt

> 用途：每完成一个 Stage 后，生成一份系统性学习笔记。
>
> 核心目标：从多个练习中提炼共同的设计问题、不同的实现方案和可迁移的工程思想，而不是简单罗列知识点。
>
> 本 Prompt 应长期复用，不针对某个特定 Stage 或框架。

---

## 一、输入材料

请尽可能结合以下材料：

1. **此前的学习对话**：包括概念讨论、代码分析、实验过程、错误修正和最终结论。
2. **本 Stage 的全部脚本**：包括练习代码、测试代码和必要的运行结果。
3. **上一 Stage 的总结笔记**：用于保持笔记结构一致，并建立新旧知识之间的联系。
4. **培养方案或学习路线**：用于理解本 Stage 在整体学习路径中的位置和目标。

如果某项材料无法访问，不要假装已经读取。明确说明缺失了什么，并仅根据现有材料总结。

### 信息可信度规则

优先级如下：

1. 实际代码及其执行结果。
2. 已经完成的实验、测试和验证记录。
3. 学习过程中已经确认的讨论结论。
4. 培养方案和课程说明。
5. 根据已有信息进行的合理推断。

必须区分：
- **代码事实**：可以直接从代码确认。
- **实验结论**：已经通过实际运行验证。
- **学习结论**：通过讨论和推导形成的理解。
- **合理推断**：有依据，但尚未验证。
- **待确认**：目前缺少足够证据。

不得将推断写成已经验证的事实。

---

## 二、总结任务

整个任务分为两个步骤。

### 第一步：提炼本 Stage 的主线

先整体审视本 Stage 的所有练习，不要立即逐个介绍。

完成以下任务：

1. 用一句话概括本 Stage 真正解决了 Agent 开发中的什么问题，而不是简单罗列学习了哪些框架。
2. 找出 3–5 条贯穿多个练习的核心母题。
3. 建立练习地图，展示每个练习的技术路线、核心机制、出口契约和验证方式。
4. 判断不同练习之间存在什么关系：递进、对照、补充，还是相对独立。
5. 找出本 Stage 相比上一 Stage 新增了什么能力，以及哪些旧知识得到了进一步应用。

母题应当是具有一定抽象程度的设计问题，例如：
- 控制流由谁决定？
- 状态由谁管理？
- 模型与程序如何分工？
- 输入和输出如何约束？
- 如何保证工具调用安全？
- 如何验证 Agent 的行为？
- 如何处理失败和恢复？

不要为了凑够 3–5 条而强行制造联系。如果某个练习确实相对独立，可以明确指出。

### 第二步：按照固定骨架生成笔记

---

## 0. 一句话主线

用不超过 40 个汉字概括本 Stage 的核心价值。

要求：
- 描述解决的问题或建立的能力。
- 不要只写框架名称或知识点列表。
- 尽可能体现本 Stage 与前一 Stage 的关系。

## 1. 练习地图

使用表格：

| 练习 | 框架/路线 | 核心机制 | 出口契约 | 验证方式 |
|---|---|---|---|---|

字段说明：

- **练习**：练习编号或名称。
- **框架/路线**：实际使用的框架、SDK 或手写实现。
- **核心机制**：本练习最值得理解的机制，控制在 1–3 个。
- **出口契约**：最终返回值、数据结构、状态或关键测试断言。
- **验证方式**：如何验证程序行为，以及是否依赖真实外部环境。

验证方式需要区分：
- 完全离线可验证。
- 通过 Mock / Fake 离线验证。
- 需要真实模型或外部 API。
- 需要 Docker、数据库或其他运行环境。
- 只能验证局部逻辑，尚未验证完整流程。

没有证据时标记「待确认」，不要根据文件名推测。

## 2. 逐练习精读

每个练习单独一节，保持以下四个固定部分。

### 2.X 练习名称

**链路：**
- 从哪个入口开始？
- 谁调用谁？
- 核心函数的执行顺序是什么？
- 最终如何返回或结束？

尽量使用具体的文件名、函数名、类名和 API。

**状态：**
- 是否存在跨步骤共享的数据？
- 状态由谁创建、读取和修改？
- 状态如何传递？
- 生命周期在哪里结束？
- 如果没有显式状态，也应明确说明。

**关键机制：**
- 本练习真正新增的 1–2 个核心机制是什么？
- 它们解决了什么问题？
- 与前面练习相比，有什么不同或进步？
- 框架提供了什么能力，开发者自己实现了什么？
- 如果没有框架与手写实现的对照，则分析程序、模型和外部服务之间的职责边界，不要强行构造对照。

**坑与边界：**
- 代码注释中特别强调了什么？
- 哪些设计存在容易忽略的限制？
- 哪些异常或边界情况值得注意？
- 当前有哪些功能尚未真正运行或验证？

只保留有学习价值的内容，不要把每个函数逐一翻译成中文。

## 3. 跨练习对照表（本 Stage 最重要的一节）

根据第一步提炼的母题，横向比较不同练习。

建议格式：

| 母题 | 练习 1 | 练习 2 | 练习 3 | 趋势 / 结论 |
|---|---|---|---|---|

要求：

1. 对比必须是同一个设计问题的不同解法，而不是简单罗列不同练习的功能。
2. 不要求所有练习都参与每个母题的比较。
3. 重点分析不同方案在控制权、职责分配、复杂度、灵活性、可观测性和可测试性上的差异。
4. 说明不同方案各自适合什么场景。
5. 尝试总结这些练习共同体现的工程规律。

优先分析以下问题：

- 框架替开发者管理了什么？
- 哪些责任仍然需要开发者亲自承担？
- 使用不同抽象层级后，代码和控制权发生了什么变化？
- 复杂度被消除了吗，还是只是转移到了其他位置？
- 哪些机制提高了可维护性、可测试性或安全性？

注意：框架与手写实现是重要对照维度，但不是所有 Stage 都必须采用的唯一对照轴。

## 4. 本 Stage 的可复用模式

提炼可以迁移到未来 Agent 项目中的设计模式。

每条采用以下结构：

### 模式 A：模式名称

- **解决的问题：** 它针对什么场景？
- **实现思路：** 核心设计是什么？
- **适用场景：** 什么时候值得使用？
- **不适用场景：** 什么时候不应该使用？
- **代码定位：** 对应的文件名、函数名或类名。

要求：

- 优先提炼真正具有迁移价值的模式。
- 不要把某个框架的 API 用法直接当成通用设计模式。
- 不要为了数量而制造模式。
- 如果某种模式只适用于特定框架或特定条件，明确说明。

## 5. 我可能没意识到的点（主动补漏）

列出 3–5 个容易忽略、但具有实际学习价值的设计决策。

每个点说明：

1. 它出现在哪里？（具体文件、函数或类）
2. 为什么值得注意？
3. 如果去掉或替换它，会发生什么？
4. 它反映了什么工程思想？

优先寻找：
- 代码中隐藏的约束。
- 框架默认行为。
- 模型与程序之间的责任边界。
- 容易混淆的参数、状态和返回值。
- 测试环境与真实环境之间的差距。
- 教学实现与生产实现之间的差距。

只有存在有意义的反例或边界时才分析，不要为了满足格式而编造。

## 6. 自测题（5–8 题）

通过题目检查是否真正理解本 Stage。

题目结构：

- 3 题概念辨析。
- 2 题读码分析。
- 1–2 题迁移设计。

要求：

1. 题目必须来自本 Stage 实际涉及的机制。
2. 读码题应尽可能引用具体函数、参数或代码行为。
3. 迁移题应要求将学到的机制应用到新的场景，而不是重复背诵。
4. 应包含容易混淆的概念和边界条件。
5. 题目后附参考答案、推理过程和常见错误。

对于重要机制，可以设置一个看起来合理、实际上错误的干扰项，检查是否真正理解。

## 7. 遗留问题 / 下个 Stage 的钩子

分为三个部分：

**本 Stage 尚未解决的问题：**
- 哪些内容没有覆盖？
- 哪些实现尚未经过真实环境验证？
- 哪些机制目前只理解了基本原理？

**值得继续深入的问题：**
- 哪些问题值得未来通过项目或实验研究？
- 哪些内容目前可以暂时作为黑盒？

**下个 Stage 的知识钩子：**
- 下一个 Stage 将解决什么新问题？
- 它可能与本 Stage 的哪些机制产生联系？
- 有哪些旧知识值得带入下一阶段？

不要仅根据课程顺序机械预测下一阶段内容，应结合实际培养方案。

---

## 三、质量规则（必须遵守）

### 1. 具体性

- 尽可能引用具体文件名、函数名、类名和 API。
- 禁止使用「某个框架」「一些代码」「某个函数」等模糊表述代替已知信息。
- 不要将 API 名称和实际机制混为一谈。

### 2. 职责边界

分析框架、程序、模型和外部服务各自承担的责任。

优先回答：
- 框架替开发者做了什么？
- 开发者仍然需要亲自完成什么？
- 模型拥有怎样的决策权？
- 哪些行为受到程序硬约束？

如果不存在明显的框架与手写实现对照，不要强行套用。

### 3. 边界与反例

核心机制必须说明至少一个重要边界：
- 去掉它会怎样？
- 参数错误会怎样？
- 什么情况下它不适用？
- 它无法解决什么问题？

辅助机制不要求机械提供反例。

### 4. 纵向一致性

- 尽量保持与上一 Stage 笔记相同的一级标题和编号。
- 固定保留 0–7 章节。
- 新内容优先放入现有章节。
- 如果确实需要增加独立主题，放入附录，并说明新增原因。
- 不要为了结构一致而保留不适用的内容。

### 5. 证据与准确性

- 不确定的地方标记「待确认」。
- 区分代码事实、实验结论和合理推断。
- 不得虚构测试结果、运行结果或代码行为。
- 不得声称已经读取没有提供的文件。
- 不得把 Mock 测试通过等同于真实环境验证通过。
- 不得把 Schema 校验通过等同于业务结果真实可靠。

### 6. 学习过程的保留

如果能够访问此前的学习对话，应当保留：

- 我曾经提出的重要问题。
- 我曾经混淆的概念。
- 我自己推导出的关键结论。
- 通过实验修正过的理解。
- 尚未完全解决的问题。

不要只输出标准教材式答案。笔记应该反映真实的学习过程和理解变化。

### 7. 内容密度

- 中文输出，代码和 API 名保留英文原文。
- 表格优先，长段落拆分为要点。
- 不要为了篇幅而重复解释同一个机制。
- 重点内容详细，辅助内容简洁。
- 主线应能快速浏览，细节应当可以按需查阅。
- 不设置僵硬的字数上限，以信息完整和阅读效率为准。

---

## 四、输出格式

直接输出完整 Markdown 笔记，不要寒暄，不要先解释总结过程。

输出顺序：

1. 一句话主线。
2. 练习地图。
3. 逐练习精读。
4. 跨练习对照。
5. 可复用模式。
6. 主动补漏。
7. 自测题。
8. 遗留问题与下个 Stage 的钩子。

开头应当让我在 30 秒内判断本 Stage 学了什么、有哪些练习，以及最值得关注的设计思想。

**最终目标：不是证明我看过多少代码，而是帮助我形成能够迁移到陌生项目中的 Agent 工程理解能力。**
