# 读懂一个脚本（SOP）

> **目的**：拿到一个新脚本后，45 分钟内弄清「它做什么 + 内部函数如何配合」
> **依据**：课程 `docs/HOW_TO_USE.md`（仅保留"读懂"部分；动手改代码属于另一次工作）
> **通过判据**：能为当前脚本画出第 2 节要求的架构图，并答出第 5 节的四问

---

## 1 定位（5 min）

### 1.1 分清类型，读法不同

| 类型 | 关注点 |
|---|---|
| `starter*.py`（产品代码） | 数据流、控制流、边界 |
| `test*.py`（验收单） | 钉住哪些契约、哪些没覆盖 |

### 1.2 找入口、出口与外部依赖

- **入口**：产品代码看 `if __name__ == "__main__":`；测试看各测试函数里的调用点
- **出口**：`return` 出来的是什么（原始值 / dict / None）
- **外部依赖**：调了几次模型 / 网络 / 文件，调用点集中在哪个函数

---

## 2 画一张架构图（15 min，本 SOP 的核心）

**关键原则：每换一个脚本就重画一张。不套用上一个脚本的图。**

### 2.1 图必须回答的 6 个问题

| # | 问题 | 在图上体现为 |
|---|---|---|
| 1 | 入口由谁调用、传什么？ | 图的起点 |
| 2 | 出口返回什么、给谁？ | 图的终点 |
| 3 | 哪些数据跨调用存活？谁创建、谁修改？ | 用 `(( ))` 圈出「状态」 |
| 4 | 每个函数做什么、谁调谁？ | 节点 + 调用边 |
| 5 | 数据在哪些环节换形状（str → dict → list[dict] …）？ | 标在边上的类型 |
| 6 | 出错或提前结束时走哪条路？ | 用 `✗` 标失败路径 |

### 2.2 图元约定

符号不求标准，只求本 SOP 内前后一致、能让不同脚本的图横向比较。

| 符号 | 含义 |
|---|---|
| `[函数名]` | 一个函数 / 一层职责 |
| `((状态名))` | 跨调用持久的数据（模块级变量、建在循环外的列表） |
| `──▶` | 调用关系 |
| `~~类型~~▶` | 数据流，边上标数据类型 |
| `◇ 条件` | 分支判断 |
| `⟲` | 循环回边 |
| `✗` | 失败 / 提前退出 |
| ⭐🟢🟡⚪ | 节点重要度（同第 3 节） |

### 2.3 画图流程

1. **列函数**：`grep "^def"` 得到节点清单（顺带拿到行数，第 3 节分层要用）
2. **从入口往下连**：先只画"谁调谁"，不画细节
3. **标数据形状**：每个函数边界写清 `入参类型 → 返回类型`（str / dict / list[dict] / SDK 对象）
4. **圈状态**：找出跨调用存活的变量——模块级全局、建在循环外的列表、被多处 `append` 的对象
5. **标分支与退出**：`if` / `for` / `return` 的落点，尤其"什么时候停"
6. **上重要度**：给节点打 ⭐🟢🟡⚪，图的阅读顺序会自动浮现

> 一张图太挤时，**分两张画**：① 调用图（谁调谁）② 数据流图（什么变成什么）。两张都画完再合看。

### 2.4 画完了吗：三个检查

- 每个函数都在图上，**包括没被任何人调用的叶子**
- 每条边有方向；涉及类型转换的边标了类型
- 沿着图能回答 2.1 的 6 个问题

缺任一条 → 图还没画完。

### 2.5 示例：一个与 agent 无关的脚本

（用来说明这套画法不是为某类脚本定制的）

```text
__main__（路径参数）
   │
   ▼
[read_file] ~~str~~▶ [parse_rows] ~~list[dict]~~▶ [summarize] ~~dict~~▶ [print_report]
                        │                              │
                        ▼                              ▼
                   ((cache))                     ◇ rows 为空？
                    写入的                       ├─ 是 → ✗ 提前返回 "no data"
                                                 └─ 否 → 继续算统计
```

三条边、一个状态、一个分支、一个失败出口。

**任何脚本的架构图都由这几类要素组成：入口、函数节点、调用/数据边、状态、分支、出口。** 变化在于脚本长什么样，而不在于画法。

## 3 按重要度分层（10 min）

| 档 | 判据 | 读法 |
|---|---|---|
| ⭐ 核心 | 删了脚本就不转；换语言/框架仍成立 | 逐行 + 对着图走 |
| 🟢 必读 | 机制所在（schema / allowlist / 验证 / 控制流） | 记契约：输入、输出、失败形式 |
| 🟡 看关键 | 只有外层几行是关键知识 | 只看外层（如 `try/except`） |
| ⚪ 可跳过 | 具体业务、环境胶水 | 黑盒，记一行签名 |

两问判据：**删掉它，脚本还能跑吗？换个场景/语言，这段还成立吗？**

**硬指标：至少一半行数应归入 ⚪。** 做不到说明还没分层。

---

## 4 只深读 ⭐ 和 🟢

- ⭐：先把 2 节画的图扩展成**时序**（每一轮状态怎么变长、靠什么停），再回代码对答案
- 🟢：只记三样——**输入、输出、失败时返回什么**
- 🟡：只看"错误怎么交给上一层"这类外层逻辑
- ⚪：一行黑盒签名，不进去

---

## 5 通用四问（判断是否真读懂）

1. **响应怎么处理**：外部返回值怎么变成下一步的输入？
2. **状态怎么累积**：谁 `append`、什么顺序、怎么配对（如 `tool_call_id`）？
3. **错误怎么处理**：抛异常 / 返回字符串 / 返回结构化数据 / 分流？
4. **什么时候停**：无输入？某个标志位？达到上限？

答不出任何一条 → 没读懂；答得出 → 这段知识可迁移。

---

## 6 收尾三句话（课程要求）

1. **为什么这样写？**
2. **拿掉它会怎样？**
3. **真实环境还缺什么？**（auth / eval / observability / retry / 人工核准）

能答才往下走；答不出只补那一条，别重读整章。

---

## 附 A：卡住怎么办

1. 看终端最上面第一个真正的错误，不要只看最后一行
2. 读本题成功条件与失败的那条测试名
3. 仍不懂 → 记一行疑问，往下走（概念会在后续练习重复出现）

## 附 B：常见坑

| 坑 | 症状 | 对策 |
|---|---|---|
| 行号引用漂移 | 注释里的行号指到别的代码 | 用函数名引用 |
| 诊断代码抢兜底 | 本该报"没点单"，却先 `TypeError` | `print` 放进 `if` 守卫 |
| 相似变量用错 | `assistant` 写成 `final_assistant` | 入历史前打印确认 |
| 测试全绿但行为已变 | mock 绕过了真实依赖 | 必须补跑真机 / eval |

## 附 C（可选）：把理解写进脚本

- 开头写**导语**：文件在做什么 / 和前后练习的关系 / 怎么跑
- 关键函数前标**重要度**（⭐🟢🟡⚪）
- **禁止写行号**，用函数名引用；注释只答"为什么"，不复述代码

---

**时间盒**：单脚本 ≤ 45 分钟。超时记一行疑问往下走——同样概念会在后续练习重复出现。
